# PostgreSQL schema (Prisma draft)

## Question

Produce the Phase 1 PostgreSQL schema as a Prisma draft in `spec.md`. The draft is not applied as a migration in this effort. Decide:

1. The concrete tables and their columns, following the ownership convention from ticket 02.
2. Column types and the amount representation from ticket 03.
3. Constraints: primary keys, foreign keys, unique constraints on the upstream reference, on the provider transaction reference, and on the idempotency key.
4. Indexes for the lookups the state machine and the Webhook Inbox need.
5. Tables required by the async boundary from ticket 06 (Outbox, Webhook Inbox, Idempotency).
6. The migration strategy for Phase 2 (for example, one initial migration versus incremental migrations).
7. The `Refund` status model and the columns that store it. Candidate values: `PENDING`, `SUCCEEDED`, `FAILED`, `REQUIRES_ACTION`. The Phase 1 port has no refund operations ([PaymentGateway port](05-gateway-plugin-contract.md)), so the asynchronous update of these statuses is left to the RefundService effort.

## Answer

Resolved in a grilling session with the user, rounds 1 to 6.

### Tables

Eight tables, all owned and written only by Core. Enum columns are native Prisma enums.

- **`core_payments`**: `id` (uuid), `merchant_order_id` (unique), `amount numeric(19,4)` with `CHECK (amount > 0)`, `currency`, `status`, `expires_at`, `created_at`, `updated_at`.
- **`core_payment_transactions`**: `id` (= `attemptKey`), `payment_id` (FK), `gateway_id` (text), `status`, `provider_ref` (nullable, unique on `(gateway_id, provider_ref)`), `provider_metadata jsonb`, `next_action jsonb` (nullable), `review_reason` (nullable enum, see below), `review_opened_at` (nullable), `refund_required boolean` (default `false`), `created_at`, `updated_at`.
- **`core_refunds`**: `id` (= `refundKey`), `payment_transaction_id` (FK), `amount numeric(19,4)` with `CHECK (amount > 0)`, `status`, `provider_ref` (nullable), `provider_metadata jsonb`, `reason` (nullable), `created_at`, `updated_at`.
- **`core_gateway_raw_responses`**: `id`, `payment_transaction_id` (FK), `operation` (text: `initiate`, `query`, `cancel`), `payload jsonb`, `created_at`. Index on `(payment_transaction_id, created_at)`.
- **`core_idempotency_keys`**: `key` (text, primary key, up to 255 chars), `request_hash`, `response_status int`, `response_body jsonb`, `payment_id` (FK, nullable), `created_at`, `expires_at`. Index on `expires_at`.
- **`core_outbox_events`**: `id` (UUID v7, also the BullMQ `jobId`), `event_type` (text), `payment_id` (FK), `payload jsonb`, `created_at`, `published_at` (nullable). Partial index on `(id) WHERE published_at IS NULL`, and an index on `published_at`.
- **`core_webhook_inbox`**: `id`, `gateway_id`, `dedupe_key`, `provider_event_id` (nullable), `attempt_key` (uuid, nullable, no FK), `raw_body bytea`, `headers jsonb` (allow-list per plugin), `query jsonb`, `status`, `attempts int` (default 0), `locked_at`, `last_error`, `received_at`, `processed_at`. Unique on `(gateway_id, dedupe_key)`. Partial indexes on `(locked_at) WHERE status = 'PROCESSING'` and `(received_at) WHERE status IN ('RECEIVED','FAILED')`. Also an index on `received_at` and an index on `attempt_key`.
- **`core_status_transitions`** (new): append-only audit trail. Columns: `id`, `entity_type`, `entity_id`, `from_status`, `to_status`, `trigger`, `actor`, `reason`, `created_at`. Written in the same database transaction as the change it records.

### Conventions

- **IDs**: `uuid`, UUID v7 generated by the application, because `attemptKey` must exist before any gateway call. PostgreSQL 18 provides `uuidv7()`, which may serve as a default for manual inserts, but the application does not rely on it.
- **Timestamps**: `timestamptz(3)`. `created_at` defaults to `now()`, and `updated_at` uses `@updatedAt`.
- **Money**: `numeric(19,4)`, stored in the currency's major unit (VND: `100000.0000`). Four decimal places cover every ISO 4217 currency. Phase 1 accepts VND only, and the application validates each currency's decimal places. The schema does not enforce them.
- **Gateway identifier**: `gateway_id` is plain `text`, not an enum.
- **Naming**: columns are snake_case via `@map`. Prisma model and field names are camelCase.
- **Foreign keys**: all `ON DELETE RESTRICT`. Nothing is cascaded, and Payments, transactions and refunds are never deleted.
- **Concurrency**: no `version` column yet. [PaymentService and Repository boundaries](08-payment-service-repository.md) decides between a row lock and an optimistic version, and may add one.

### Constraints and partial indexes

The following are written as raw SQL in the migration, because Prisma cannot declare partial indexes:

- **Invariant 6a**: `UNIQUE (payment_id) WHERE status IN ('CREATED','PENDING')`. At most one attempt is open per Payment.
- **Invariant 7**: `UNIQUE (payment_id) WHERE status = 'SUCCEEDED'`. At most one attempt succeeds per Payment.
- **Invariant 5**: `UNIQUE (gateway_id, provider_ref)` on `core_payment_transactions`.
- **Invariant 2**: `UNIQUE (merchant_order_id)` on `core_payments`.
- **Expiry sweep**: an index on `(status, expires_at) WHERE status = 'PENDING'`.

A Vitest spec asserts that these indexes exist, so they cannot be dropped silently.

**Invariant 6b** (`REQUIRES_REVIEW` blocks new attempts) is enforced by the service under the Payment row lock, not by the database.

### Review handling

- `review_reason` is an enum with four values: `AMBIGUOUS_PROVIDER_STATUS`, `AMOUNT_MISMATCH`, `LATE_SUCCESS_ON_CLOSED_PAYMENT`, `DUPLICATE_SUCCESS`. It is set when an attempt enters `REQUIRES_REVIEW`. `review_opened_at` records when that happened.
- **Automatic**: `AMBIGUOUS_PROVIDER_STATUS` and `AMOUNT_MISMATCH` are re-queried on schedule. A clear answer is applied with the normal rules.
- **Operator, after 72 hours** without a clear answer. The operator may only set `SUCCEEDED` (if the amount equals `Payment.amount` and the Payment is `PENDING`) or `FAILED`. For `AMOUNT_MISMATCH` this means only `FAILED` is possible. A note is mandatory, and the action is recorded in `core_status_transitions`.
- **`refund_required`** is set to `true` whenever money was collected but the attempt is not `SUCCEEDED`.
- **`LATE_SUCCESS_ON_CLOSED_PAYMENT` and `DUPLICATE_SUCCESS`** stay `REQUIRES_REVIEW` with `refund_required = true` until the RefundService effort exists. Until then, operators may only add notes.

### Refund status

- `RefundStatus`: `PENDING`, `SUCCEEDED`, `FAILED`, `REQUIRES_ACTION`, `CANCELLED`.
- `PENDING` and `REQUIRES_ACTION` are non-terminal. The rest are terminal.
- Mapping from provider statuses (VNPay and ZaloPay "processing" maps to `PENDING`) and the transitions belong to the RefundService effort.
- Invariants 10 and 11 are enforced by RefundService under the Payment row lock. `FAILED` and `CANCELLED` refunds are not counted toward the total.
- Phase 1 has no code that writes `core_refunds`. The table exists so that RefundService needs no breaking change.

### Migration

- A single initial migration, `0001_payment_core`, contains Prisma's generated DDL and the raw SQL above.
- After the first deploy to any shared environment, only forward-only migrations are allowed. A migration that has run is never edited.
- Before the first deploy, `0001` may be regenerated.
- A Phase 2 spike confirms that `prisma migrate dev` does not try to drop the raw indexes. If it does, the fallback is the Vitest spec plus a CI step running `migrate diff`.
- Multi-Merchant later is a separate migration that adds `merchant_id` and changes the uniqueness of `merchant_order_id`.

### Deferred

- Row lock versus version column, and the locking between the sweep, webhooks and merchant actions: [PaymentService and Repository boundaries](08-payment-service-repository.md).
- The RefundService flow and refund status mapping: a later effort.
- Provider behaviours that research could not verify: the map's Not yet specified section.
