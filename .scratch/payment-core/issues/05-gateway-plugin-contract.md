# PaymentGateway port (Core-owned contract)

## Question

Define the `PaymentGateway` port that Payment Core owns and every plugin implements. Decide:

1. The operations (for example: create a transaction, query status, parse and verify a callback or webhook, refund).
2. Input and output shapes in provider-neutral terms: which fields are required, and where provider-specific data goes as an explicit extension field.
3. The error taxonomy the port exposes, so Core can react without knowing the provider.
4. How a plugin is registered, and how the Gateway Manager resolves it by gateway identifier.
5. The rule that plugins depend on the port only and Core never imports a plugin. How this is enforced (module boundary, lint rule, or both).

Check the port against the research findings. If a provider cannot fit the port without leaking its own concepts into Core, record it as a question for this ticket.

## Answer

Resolved in a grilling session with the user, rounds 1 to 3.

### Operations

The port has four operations: `initiate`, `query`, `cancel` and `parseCallback`. Refund operations (`createRefund`, `queryRefund`) are not part of the Phase 1 port. The RefundService effort adds them later as an extension. The Phase 1 `Refund` status model is decided in [PostgreSQL schema](07-postgres-schema.md).

### Registration and enforcement

- Each Gateway Plugin is a class that implements the port and declares a constant `gatewayId` (`vnpay`, `zalopay`, `stripe`).
- Plugins are registered explicitly in the composition root (a Nest module). There is no auto-scan.
- The Gateway Manager builds a map `gatewayId -> plugin` at boot and fails fast on a duplicate or a missing plugin.
- Core resolves the plugin from `PaymentTransaction.gatewayId`.
- A CI lint rule (ESLint `no-restricted-imports` or dependency-cruiser) forbids Core modules from importing the plugin directory. The composition root is the only exception.
- Core exports no plugin types. Core knows only the port and the types the port defines.

### initiate

- Input: `attemptKey` (UUID v7 generated by Core; the plugin formats the gateway-facing value), `amount` (decimal VND, whole dong; see [Domain model and invariants](03-domain-model-invariants.md)), `currency`, `expiresAt`, `returnUrl`, `description`.
- Output: `{ providerRef?, nextAction, providerMetadata, rawPayload }`.
- `NextAction` is a discriminated union with four variants: `REDIRECT { url }`, `QR_CODE { payload }`, `CLIENT_SDK { token }`, `VOUCHER { details }`. `VOUCHER` is kept in Phase 1 so that adding a variant later does not break the union, even if no Phase 1 method uses it.
- `providerRef` is nullable.

### Extension fields

- `providerMetadata` is an opaque JSON bag. Core stores it on `PaymentTransaction.providerMetadata`, passes it back to the plugin on later calls, and never interprets it. Example: VNPay `vnp_CreateDate`, which `query` needs.
- `rawPayload` is the provider's original response. Core writes it to `core_gateway_raw_responses` (see [Table ownership convention](02-table-ownership-convention.md)).

### query and cancel

- Input: `attemptKey` and the attempt's `providerMetadata`. There is no separate `providerRef` input.
- Each plugin declares capability flags (for example `supportsCancel`). Core checks the flag before calling. `UnsupportedOperation` is a defensive error, not a normal path.

### Normalized outcome

- `query` and `parseCallback` return one of `PENDING`, `SUCCEEDED`, `FAILED` or `REQUIRES_REVIEW`, together with the `amount` the provider reports.
- `EXPIRED` and `CANCELLED` are decided by Core, as defined in the [state machine](04-payment-state-machine.md). Plugins do not report them.
- Plugins map provider codes to these four states. Examples: ZaloPay `return_code=3` is `PENDING`; ZaloPay `-54` is `FAILED` with `rawCode`; VNPay `07` or `04` is `REQUIRES_REVIEW`.
- Core compares the reported `amount` with `Payment.amount`.

### Error taxonomy

Five categories, each with a `retryable` flag:

- `GatewayRejected`: the provider rejects clearly (for example a ZaloPay synchronous reject). Not retryable. Core moves the attempt to `FAILED`.
- `GatewayUnavailable`: timeout, 5xx or network error before the provider accepted the request. Retryable. The attempt state does not change.
- `OutcomeUnknown`: timeout after the request was sent, when it is not known whether the provider accepted it. Not retried directly. Core keeps the attempt, and the scheduler re-queries it. Kept separate from `GatewayUnavailable` so that Core does not treat it as a failure.
- `InvalidCallback`: signature or payload is invalid. The plugin returns an error ack and nothing is processed.
- `NotFound`: `query` finds no transaction (for example VNPay `91`). Returned to Core to decide.

### Stripe decline absorption

A Stripe decline is absorbed inside one attempt. It does not end the attempt, and the customer may retry on the same PaymentIntent. Core sees `PENDING` until the PaymentIntent reaches `succeeded`, or until Core closes the attempt through `cancel` or expiry. In that case the plugin reports `FAILED`. Core never sees `requires_payment_method`.

### parseCallback

- Input: raw body bytes, headers and query parameters.
- Output: `attemptKey`, `normalizedStatus`, `amount`, `providerRef?`, `providerEventId?`, `ackPayload`.
- The plugin derives `attemptKey` from provider data (VNPay `vnp_TxnRef`, ZaloPay `app_trans_id`, Stripe `metadata.attempt_key`), so Core never reads provider-specific identifiers.
- `ackPayload` is built by the plugin in the provider's format (VNPay `RspCode`, ZaloPay `return_code`, Stripe HTTP 200).
- Where signature verification sits relative to persistence is decided in [Async reliability boundary](06-async-reliability-boundary.md).
