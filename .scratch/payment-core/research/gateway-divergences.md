# Gateway Divergences: VNPay, ZaloPay, and Stripe

This document records primary-source findings on behaviours of **VNPay**, **ZaloPay**, and **Stripe** that would break a provider-neutral `PaymentGateway` port or a `Payment` / `PaymentTransaction` state machine if assumed away. All sources were verified on **2026-11-23**.

## Summary

- **Initiation & presentation payloads differ fundamentally**: VNPay builds a signed redirect URL purely client/server-side with no HTTP call to VNPay; ZaloPay performs a synchronous `POST /v2/create` returning `order_url`, `zp_trans_token`, `order_token`, and a raw VietQR string (`qr_code`) simultaneously; Stripe offers either `PaymentIntent` (`client_secret` + polymorphic `next_action` redirect/QR/voucher objects, optionally confirmed synchronously) or `CheckoutSession` (hosted `url` or embedded `client_secret`).
- **Provider references are generated at different times with different uniqueness scopes**: VNPay's `vnp_TxnRef` is merchant-generated and unique only per GMT+7 day, while `vnp_TransactionNo` is absent until payment completion; ZaloPay's `app_trans_id` is merchant-generated with a mandatory GMT+7 `yymmdd_` prefix, while `zp_trans_id` does not exist at `/v2/create` time (only appearing after user confirmation, yet required for `/v2/refund`); Stripe generates globally unique opaque IDs (`pi_...`, `cs_...`, `ch_...`, `re_...`) up to 255 characters immediately on creation.
- **VND unit scaling conflicts 100x**: ZaloPay (`amount`) and Stripe (`vnd`, a zero-decimal currency) expect integer VND (`100000` = 100,000 VND), whereas VNPay (`vnp_Amount`) requires multiplying VND by `100` (`10000000` = 100,000 VND).
- **Status models and failure/expiry visibility diverge sharply**: ZaloPay **never** sends callbacks on failure or expiry (requiring proactive `/v2/query` polling); Stripe `PaymentIntent` resets backward to `requires_payment_method` on decline (allowing multiple `Charge` attempts on one `PaymentIntent`), supports two-step `requires_capture`, and **has no automatic expiry** outside `CheckoutSession` (`expires_at`) or manual-capture holds (7 days); both Stripe (e.g., Konbini / delayed bank methods) and potentially VNPay/ZaloPay edge cases expose late-settlement hazards around expiry.
- **Refunds are asynchronous and lack uniform idempotency**: VNPay and ZaloPay refunds return intermediate processing states without a refund webhook (requiring `querydr` / `/v2/query_refund` polling), lack `Idempotency-Key` replay headers, and restrict partial refunds (VNPay blocks full refund after partial refund; ZaloPay rejects partial refunds on non-ZaloPay wallets and promoted transactions); Stripe supports multiple partial refunds, async `pending`/`requires_action`/`failed` states with `refund.*` webhooks, and 24-hour `Idempotency-Key` response caching.

## VNPay

### 1. Payment initiation response shape and synchronicity

- For standard VNPay Payment Gateway (`vnp_Command=pay`, v2.1.0), initiation does **not** make an HTTP API call to VNPay: the merchant server synchronously constructs and signs a `GET` redirect URL (`https://sandbox.vnpayment.vn/paymentv2/vpcpay.html?...&vnp_SecureHash=...`) and redirects the customer's browser to it ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- No QR payload or client secret is returned to the merchant server at initiation; setting `vnp_BankCode` optionally pre-selects `VNPAYQR`, `VNBANK`, or `INTCARD` on VNPay's hosted UI, and merchants wanting to list banks before redirecting call `POST https://sandbox.vnpayment.vn/qrpayauth/api/merchant/get_bank_list` ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- **UNVERIFIED**: Whether VNPay exposes a separate server-to-server dynamic VNPAY-QR initiation endpoint outside `vpcpay.html` (and exact production hostname formatting beyond sandbox host replacement) could not be verified because the index page `https://sandbox.vnpayment.vn/apis/` returned HTTP 504 when fetched (accessed 2026-11-23).

### 2. Provider transaction reference

- **Merchant-generated attempt reference (`vnp_TxnRef`)**: `Alphanumeric[1,100]`, required in `pay`, Return URL, IPN, `querydr`, and `refund`. VNPay specifies it is unique to distinguish orders sent to VNPay and *"Không được trùng lặp trong ngày"* (must not repeat within the same GMT+7 day) ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23). Uniqueness is scoped per `vnp_TmnCode` per day.
- **Provider-generated transaction reference (`vnp_TransactionNo`)**: `Numeric[1,15]` (e.g., `20170829153052`), assigned by VNPay and returned via Return URL, IPN, `querydr`, and `refund` ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23). It is unavailable at initiation because no server call occurs. An optional `vnp_BankTranNo` (`Alphanumeric[1,255]`) carries the bank-side reference ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- **Query/Refund request IDs**: `vnp_RequestId` (`Alphanumeric[1,32]`, merchant-generated, unique per day) and `vnp_ResponseId` (`Alphanumeric[1,32]`, VNPay-generated, unique per day) ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- **UNVERIFIED**: What value `vnp_TransactionNo` takes (e.g., `"0"` vs empty vs assigned numeric ID) when a payment fails before reaching a bank or expires; [VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html) marks it required on IPN/Return URL while [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html) marks it optional on requests (accessed 2026-11-23).

### 3. Amount and currency units for VND

- `vnp_CurrCode` (`Alpha[3]`) currently supports **`VND` only** ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- `vnp_Amount` (`Numeric[1,12]`) **must be multiplied by 100** to eliminate decimals (e.g., `10,000 VND` is sent as `1000000`), and VNPay returns `vnp_Amount` scaled by `100` in IPN, Return URL, `querydr`, and `refund` ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay FAQs](https://sandbox.vnpayment.vn/apis/docs/faqs/), accessed 2026-11-23; [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- Minimum payment amount is **5,000 VND**; maximum depends on the customer's bank limits ([VNPay FAQs](https://sandbox.vnpayment.vn/apis/docs/faqs/), accessed 2026-11-23) and the 12-digit wire length.

### 4. Status model and late success after expiry

- VNPay v2.1.0 exposes **two status fields** across Return URL, IPN, and `querydr`:
  - `vnp_ResponseCode` (`Numeric[2]`): `00` = success; `07` = customer debited, transaction suspected of fraud/anomaly (*"Trừ tiền thành công. Giao dịch bị nghi ngờ"*); `09, 10, 11, 12, 13, 24, 51, 65, 75, 79, 99` = specific bank/customer failures, cancellation (`24`), or payment timeout (`11`) ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay Error Codes](https://sandbox.vnpayment.vn/apis/docs/bang-ma-loi/), accessed 2026-11-23). On `querydr` and `refund`, `vnp_ResponseCode=00` indicates the **API call** succeeded, not the payment itself ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
  - `vnp_TransactionStatus` (`Numeric[2]`): `00` = payment succeeded; `01` = incomplete/in-progress (non-terminal); `02` = error/failed; `04` = reversal (*"Giao dịch đảo"* — customer was debited at bank but transaction failed at VNPay); `05` = VNPay processing refund; `06` = VNPay sent refund to bank; `07` = suspected fraud; `09` = refund rejected ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- Notice VNPay's own documentation exhibits sample inconsistency (`pay.html` PHP checks `vnp_ResponseCode == '00' || vnp_TransactionStatus == '00'` while C# checks `&&`), and codes `07` (suspected fraud debit) and `04` (bank-debited reversal) represent non-binary outcomes requiring manual review/reconciliation rather than simple failure ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- **Late success after expiry**: `vnp_ResponseCode=11` indicates payment wait timeout ([VNPay Error Codes](https://sandbox.vnpayment.vn/apis/docs/bang-ma-loi/), accessed 2026-11-23). **UNVERIFIED**: Whether VNPay can ever emit a late `00` IPN (or transition `01`/`11` -> `00`) after `vnp_ExpireDate` passes (e.g., due to delayed bank confirmation right at expiry) is not stated in VNPay's public documentation (accessed 2026-11-23).

### 5. Final result delivery, authoritativeness, signature scheme, and retry

- **Return URL (`vnp_ReturnUrl`, `GET`) vs IPN URL (`GET`, SSL required)**: Both receive the same `vnp_*` query parameters, but VNPay mandates that `vnp_ReturnUrl` is **only** for signature check and UI display—status updates in the database **must** happen on the server-to-server **IPN URL** ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay Connection Model](https://sandbox.vnpayment.vn/apis/docs/mo-hinh-ket-noi/), accessed 2026-11-23; [VNPay FAQs](https://sandbox.vnpayment.vn/apis/docs/faqs/), accessed 2026-11-23).
- **Pull reconciliation (`querydr`)**: `POST https://sandbox.vnpayment.vn/merchant_webapi/api/transaction` with `vnp_Command=querydr` queries transaction state ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23). If the user never opened the VNPay URL, `querydr` returns `vnp_ResponseCode=91` (transaction not found) ([VNPay Error Codes](https://sandbox.vnpayment.vn/apis/docs/bang-ma-loi/), accessed 2026-11-23).
- **Signature scheme**: In v2.1.0, `vnp_SecureHash` uses **`HMAC-SHA512`** with `vnp_HashSecret` over ascending-sorted `vnp_*` parameters (excluding `vnp_SecureHash` and `vnp_SecureHashType`), URL-encoded as `key=value` joined by `&` (`vnp_SecureHashType` is no longer sent on v2.1.0 requests) ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay Hash Migration](https://sandbox.vnpayment.vn/apis/docs/chuyen-doi-thuat-toan/changeTypeHash.html), accessed 2026-11-23). For `querydr` and `refund` JSON APIs, `vnp_SecureHash` signs a fixed pipe-delimited (`|`) string of specified fields ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- **IPN retry and acknowledgment**: Merchant must return JSON `{"RspCode": "...", "Message": "..."}`. VNPay **stops retrying** on `RspCode` `00` (Confirm Success) or `02` (Order already confirmed). On `01`, `04`, `97`, `99`, or IPN timeout, VNPay retries up to **10 times** at **5-minute intervals** ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).

### 6. Expiry or timeout of an unpaid attempt

- `vnp_ExpireDate` (`Numeric[14]`, `yyyyMMddHHmmss` in **GMT+7**) is documented as **required** in v2.1.0 `pay` parameters (PHP/C#/Java samples set `now + 15 minutes`, though the Node.js sample omits it) ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- VNPay documents no server-side "cancel unpaid redirect" API ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- **UNVERIFIED**: Whether VNPay automatically fires an IPN (`vnp_ResponseCode=11`) when an untouched/abandoned payment URL passes `vnp_ExpireDate` without user interaction, and what minimum/maximum `vnp_ExpireDate` window VNPay enforces, are not stated in VNPay's public docs (accessed 2026-11-23).

### 7. Refund API

- `POST https://sandbox.vnpayment.vn/merchant_webapi/api/transaction` with `vnp_Command=refund` ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23).
- **Partial & multiple refunds**: Supports full (`vnp_TransactionType=02`) and partial (`vnp_TransactionType=03`) refunds ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23). Error codes `02` (*"Tổng số tiền hoàn trả lớn hơn số tiền gốc"* = cumulative refunds exceed original amount) and `04` (*"Không cho phép hoàn trả toàn phần sau khi hoàn trả một phần"* = full refund `02` forbidden after partial refund `03`) confirm multiple partial refunds are tracked cumulatively, while `13` (*"Chỉ cho phép hoàn trả một phần"*) applies to methods permitting partial refunds only ([VNPay Error Codes](https://sandbox.vnpayment.vn/apis/docs/bang-ma-loi/), accessed 2026-11-23).
- **Asynchronous completion**: `refund` can leave the refund in `vnp_TransactionStatus` `05` (processing at VNPay) or `06` (sent to bank), later resolving to `00` or `09` (rejected) ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23). No refund webhook/IPN is documented in [VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html) or [VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html) (accessed 2026-11-23); status must be polled via `querydr`. (**UNVERIFIED**: Whether VNPay offers private/undocumented refund webhooks.)
- **Idempotency**: No `Idempotency-Key` header. Requests require a merchant-generated `vnp_RequestId` unique within the day. Duplicate requests within a **5-minute** API window return error code `94` (*"Yêu cầu bị trùng lặp trong thời gian giới hạn của API (Giới hạn trong 5 phút)"* / already processing) rather than replaying the prior refund payload ([VNPay QueryDr & Refund API](https://sandbox.vnpayment.vn/apis/docs/truy-van-hoan-tien/querydr&refund.html), accessed 2026-11-23; [VNPay Error Codes](https://sandbox.vnpayment.vn/apis/docs/bang-ma-loi/), accessed 2026-11-23).

### 8. Duplicate callback or webhook behaviour

- VNPay retries IPNs up to 10 times (5 minutes apart) whenever it receives non-`00`/`02` `RspCode` or timeouts ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- There is no webhook event ID; deduplication relies on `vnp_TxnRef` (and `vnp_TransactionNo`). The merchant's IPN handler must detect already-confirmed transactions and respond with `RspCode: "02"` (`Order already confirmed`), which VNPay treats identically to `"00"` to stop retries ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23).
- Browser `vnp_ReturnUrl` and server IPN can race in either order ([VNPay Pay API](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html), accessed 2026-11-23; [VNPay Connection Model](https://sandbox.vnpayment.vn/apis/docs/mo-hinh-ket-noi/), accessed 2026-11-23).

## ZaloPay

### 1. Payment initiation response shape and synchronicity

- Synchronous server-to-server call: `POST https://openapi.zalopay.vn/v2/create` (sandbox: `https://sb-openapi.zalopay.vn/v2/create`) ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23; [ZaloPay v2 Overview](https://developer.zalopay.vn/v2/general/overview.html), accessed 2026-11-23).
- On `return_code = 1`, ZaloPay synchronously returns multiple presentation fields in the same JSON payload: `order_url` (redirect URL to ZaloPay Gateway or input to render a QR), `zp_trans_token` and `order_token` (mobile SDK / token-payment tokens), and `qr_code` (EMVCo / NAPAS VietQR string scannable by ZaloPay and 40+ NAPAS bank apps) ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23; [ZaloPay Gateway Guide](https://docs.zalopay.vn/docs/guides/payment-acceptance/payment-gateway/intro), accessed 2026-11-23).
- **Critical absence**: `/v2/create` does **not** return `zp_trans_id` ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23).

### 2. Provider transaction reference

- **Merchant-generated order reference (`app_trans_id`)**: `String(40)`, required on `/v2/create`, `/v2/query`, `/v2/cancel`, and returned in callbacks/redirects. Must begin with **`yymmdd`** of the current date in **Vietnam timezone (GMT+7)** (e.g., `250210_OrderID`) ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23). Must be unique; submitting a duplicate `app_trans_id` fails `/v2/create` with `return_code = 2, sub_return_code = -68` (`DUPLICATE_APPS_TRANS_ID`) ([ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23; [ZaloPay v2 Overview](https://developer.zalopay.vn/v2/general/overview.html), accessed 2026-11-23).
- **Provider-generated transaction reference (`zp_trans_id`)**: `int64` / `Long` (documented max length 15 in refund spec, e.g., `220420000029880`), **initiated only when the user confirms payment at ZaloPay** and returned only in the success callback or `/v2/query` response ([ZaloPay Query Order](https://docs.zalopay.vn/docs/specs/order-query), accessed 2026-11-23; [ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf), accessed 2026-11-23). `zp_trans_id` is **required** to call `/v2/refund` ([ZaloPay Refund](https://docs.zalopay.vn/docs/specs/order-refund), accessed 2026-11-23).
- **Refund references**: Merchant-generated `m_refund_id` (`String(45)`, format `yymmdd_appid_xxxxxxxxxx`); ZaloPay-generated `refund_id` (`int64` / `Long`) returned by `/v2/refund` ([ZaloPay Refund](https://docs.zalopay.vn/docs/specs/order-refund), accessed 2026-11-23; [ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf), accessed 2026-11-23).

### 3. Amount and currency units for VND

- `amount` is `int64` / `Long` in **integer VND** (zero-decimal; e.g., `50000` = 50,000 VND) ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23). No `×100` scaling is used.
- `currency` is omitted from the current `docs.zalopay.vn` `/v2/create` schema ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23) and documented in the Integration PDF as defaulting to `VND` ([ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf), accessed 2026-11-23).

### 4. Status model and late success after expiry

- **API/Query `return_code`**: `1` (`SUCCESS`), `2` (`FAIL`), `3` (`PROCESSING` — unpaid or processing), plus `is_processing: boolean` and `sub_return_code` ([ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23; [ZaloPay Query Order](https://docs.zalopay.vn/docs/specs/order-query), accessed 2026-11-23).
- Non-terminal failure during validity window: e.g., `sub_return_code = -63` (`ZPW_BALANCE_NOT_ENOUGH`) means the order is unpaid and if unexpired, the user can top up and retry payment ([ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23).
- Terminal states: Paid (`return_code = 1`), Expired (`sub_return_code = -54 TIME_INVALID`), Failed (`return_code = 2`), or Merchant-Canceled (`POST /v2/cancel`, after which the order can no longer be paid; canceling an already-paid order fails with `-403 ORDER_ALREADY_CAPTURED`) ([ZaloPay Cancel Order](https://docs.zalopay.vn/docs/specs/order-cancel), accessed 2026-11-23; [ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23).
- **Late success after expiry**: Docs state an order expires and is marked `INVALID` after 15 minutes (or `expire_duration_seconds`) and advise merchants to stop polling and mark unpaid orders failed after that window ([ZaloPay Dynamic QR](https://docs.zalopay.vn/docs/guides/payment-acceptance/qrcode/dynamic-qr), accessed 2026-11-23). **UNVERIFIED**: Whether a transaction in `is_processing = true` (`return_code = 3`) initiated just before expiry can settle late and still deliver a success callback after the nominal expiry timestamp is not documented.

### 5. Final result delivery, authoritativeness, signature scheme, and retry

- **Success-only push callback (`POST` JSON)**: ZaloPay sends `callback_url` notifications **only when payment succeeds** (*"After Zalopay successfully deducts the money, it will notify..."*); no callback is sent on user failure, cancellation, or expiration ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23; [ZaloPay Callback](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/callback), accessed 2026-11-23).
- **Browser redirect (`embed_data.redirecturl`, `GET`)**: Passes `appid`, `apptransid`, `pmcid`, `bankcode`, `amount`, `discountamount`, `status`, `checksum` (verified with `key2`), but ZaloPay instructs merchants to check whether the callback arrived and otherwise call **`/v2/query`** before treating the result as final ([ZaloPay Gateway Guide](https://docs.zalopay.vn/docs/guides/payment-acceptance/payment-gateway/intro), accessed 2026-11-23).
- **Mandatory polling fallback**: Because failure/expiry emit no callback and callbacks can be missed, ZaloPay explicitly recommends polling `/v2/query` (e.g., once per minute until callback or expiry, or at least once after the 15-minute window) ([ZaloPay Query Order](https://docs.zalopay.vn/docs/specs/order-query), accessed 2026-11-23; [ZaloPay Gateway Guide](https://docs.zalopay.vn/docs/guides/payment-acceptance/payment-gateway/intro), accessed 2026-11-23).
- **Asymmetric HMAC keys (`key1` vs `key2`)**: Default `HmacSHA256` throughout, but outbound requests use **`key1`** (pipe-delimited fields) while inbound callbacks (`HMAC(key2, body.data)`) and redirect checksums use **`key2`** ([ZaloPay Secure Transmission](https://docs.zalopay.vn/docs/developer-tools/security/secure-data-transmission), accessed 2026-11-23; [ZaloPay Callback](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/callback), accessed 2026-11-23).
- **Callback retry & response**: Docs contain an internal contradiction: the [ZaloPay Callback](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/callback) response table lists `1` (Success) and `2` (Failed), the [ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf) lists `1` (Success), `2` (Duplicate `zp_trans_id` or `app_trans_id`), `<>` (failure, do not retry), while all official code examples in [ZaloPay Callback](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/callback) and [ZaloPay v2 Overview](https://developer.zalopay.vn/v2/general/overview.html) set `return_code = 0` on exception with the comment *"callback again (up to 3 times)"* (accessed 2026-11-23). **UNVERIFIED**: The exact retry interval / backoff schedule between the up-to-3 retries is not documented.

### 6. Expiry or timeout of an unpaid attempt

- `/v2/create` accepts `expire_duration_seconds` (`long`), valid from **`300` seconds (5 minutes) to `2592000` seconds (30 days)** ([ZaloPay Create Order](https://docs.zalopay.vn/docs/specs/order-create), accessed 2026-11-23).
- When omitted, the default validity window is **15 minutes** ([ZaloPay Query Order](https://docs.zalopay.vn/docs/specs/order-query), accessed 2026-11-23; [ZaloPay Dynamic QR](https://docs.zalopay.vn/docs/guides/payment-acceptance/qrcode/dynamic-qr), accessed 2026-11-23).
- Merchants can actively terminate an unpaid order before expiry via `POST /v2/cancel` ([ZaloPay Cancel Order](https://docs.zalopay.vn/docs/specs/order-cancel), accessed 2026-11-23).

### 7. Refund API

- `POST /v2/refund` requires `zp_trans_id` (not `app_trans_id`), `m_refund_id` (`yymmdd_appid_xxx`), `amount`, `timestamp` (Unix ms; must be within 15 minutes or fails with `-13 ORDER_REFUND_EXPIRED`), optional `refund_fee_amount`, `description`, and `mac` ([ZaloPay Refund](https://docs.zalopay.vn/docs/specs/order-refund), accessed 2026-11-23; [ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23).
- **Partial refunds**: Supported in general (*"hoàn tiền toàn phần hoặc từng phần"*) ([ZaloPay v2 Overview](https://developer.zalopay.vn/v2/general/overview.html), accessed 2026-11-23), **except** rejected with `-32 NOT_SUPPORT_PARTIAL_REFUND` for non-ZaloPay e-wallet payments ([ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes), accessed 2026-11-23), and **forbidden** on orders with ZaloPay or partner promotions (*"The required refund amount must be a full refund"*) ([ZaloPay FAQs](https://docs.zalopay.vn/docs/faq), accessed 2026-11-23; [ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf), accessed 2026-11-23).
- **Multiple refunds per payment**: **UNVERIFIED**—public `docs.zalopay.vn` and `developer.zalopay.vn` specs do not explicitly confirm whether multiple sequential partial refunds against one `zp_trans_id` are allowed or capped (accessed 2026-11-23).
- **Asynchronous completion**: Explicitly asynchronous—`/v2/refund` *"only confirms that the refund request has been received"* and returns `return_code` `1` (Success), `2` (Fail), or `3` (Processing); merchants must poll `POST /v2/query_refund` with `m_refund_id` to obtain the final result ([ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes) includes `-1 REFUND_PENDING`, `-16 INSERT_REFUND_LOG_AR_FAIL`; bank/card refunds settle in 3–7 business days) ([ZaloPay Refund](https://docs.zalopay.vn/docs/specs/order-refund), accessed 2026-11-23; [ZaloPay Query Refund](https://docs.zalopay.vn/docs/specs/order-query-refund), accessed 2026-11-23; [ZaloPay FAQs](https://docs.zalopay.vn/docs/faq), accessed 2026-11-23). No refund webhook exists.
- **Idempotency key support**: No `Idempotency-Key` header. `m_refund_id` identifies each refund request ([ZaloPay Refund](https://docs.zalopay.vn/docs/specs/order-refund), accessed 2026-11-23). **UNVERIFIED**: Public [ZaloPay Status Codes](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/status-codes) do not document what `/v2/refund` returns if the exact same `m_refund_id` is submitted twice (no `DUPLICATE_M_REFUND_ID` code appears under Refund Order, accessed 2026-11-23).

### 8. Duplicate callback or webhook behaviour

- ZaloPay warns that callback endpoints *"may receive duplicate events"* and requires idempotent handling ([ZaloPay Callback](https://docs.zalopay.vn/docs/developer-tools/knowledge-base/callback), accessed 2026-11-23).
- Callback payloads contain **no event ID**; deduplication must key on `data.app_trans_id` and/or `data.zp_trans_id`. Returning `{"return_code": 2, ...}` explicitly signals a duplicate `zp_trans_id` / `app_trans_id` that was already fulfilled ([ZaloPay Integration PDF](https://developer.zalopay.vn/downloads/api/ZaloPay-APIs-Integration-Document.pdf), accessed 2026-11-23).

## Stripe

### 1. Payment initiation response shape and synchronicity

- Stripe exposes two primary initiation models, both via synchronous `POST` API calls ([Compare Checkout Sessions and Payment Intents](https://docs.stripe.com/payments/checkout-sessions-and-payment-intents-comparison), accessed 2026-11-23):
  - **PaymentIntents API** (`POST /v1/payment_intents`): Returns a `PaymentIntent` containing `client_secret` (used by Stripe.js / mobile SDKs). If created with `confirm=true` and a `payment_method`, it attempts payment synchronously and can return `status: succeeded`, `requires_capture`, `processing`, `requires_payment_method` (instant failure), or `requires_action` with a payment-method-specific `next_action`—such as `next_action.redirect_to_url.url`, `next_action.use_stripe_sdk`, QR payloads (`wechat_pay_display_qr_code`, `pix_display_qr_code`, `paynow_display_qr_code`, `promptpay_display_qr_code`), or voucher details (`konbini_display_details`, `boleto_display_details`, `oxxo_display_details`) ([Create a PaymentIntent](https://docs.stripe.com/api/payment_intents/create), accessed 2026-11-23; [Confirm a PaymentIntent](https://docs.stripe.com/api/payment_intents/confirm), accessed 2026-11-23; [The PaymentIntent Object](https://docs.stripe.com/api/payment_intents/object), accessed 2026-11-23).
  - **Checkout Sessions API** (`POST /v1/checkout/sessions`): Returns a `CheckoutSession` with a hosted redirect `url` (`ui_mode: hosted_page`) or `client_secret` (`ui_mode: embedded_page` / `elements`). Its `payment_intent` field can initially be `null` until checkout confirmation occurs ([Create a Checkout Session](https://docs.stripe.com/api/checkout/sessions/create), accessed 2026-11-23; [The Checkout Session Object](https://docs.stripe.com/api/checkout/sessions/object), accessed 2026-11-23).

### 2. Provider transaction reference

- **Provider-generated**: Stripe generates all identifiers (`pi_...` for PaymentIntent, `cs_...` for CheckoutSession, `ch_...` for Charge, `re_...` for Refund, `evt_...` for Event); merchant references are attached via `metadata` or `client_reference_id` (max 200 chars on CheckoutSession) ([The PaymentIntent Object](https://docs.stripe.com/api/payment_intents/object), accessed 2026-11-23; [Create a Checkout Session](https://docs.stripe.com/api/checkout/sessions/create), accessed 2026-11-23).
- **Format, length, and uniqueness**: Opaque, case-sensitive strings up to **255 characters** (Stripe warns not to hardcode prefix formats or shorter column lengths as backwards-compatible upgrades may vary them) ([Stripe API Upgrades](https://docs.stripe.com/upgrades?since=2016-03-07), accessed 2026-11-23). Uniqueness is global across Stripe (not day-scoped). A single `PaymentIntent` can accumulate multiple `Charge` objects (`latest_charge` points to the latest attempt) if retried after declines ([Verifying Payment Status](https://docs.stripe.com/payments/payment-intents/verifying-status), accessed 2026-11-23).

### 3. Amount and currency units for VND

- Stripe designates **`vnd` as a zero-decimal currency** (`BIF, CLP, DJF, GNF, JPY, KMF, KRW, MGA, PYG, RWF, UGX, VND, VUV, XAF, XOF, XPF`): `amount` must be passed directly in integer dong (e.g., `100000` for `100,000 VND`, lowercase `currency: "vnd"`) without multiplying by 100 ([Supported Currencies](https://docs.stripe.com/currencies), accessed 2026-11-23).
- Minimum charge is **US $0.50 equivalent** in the account's settlement currency (or higher per payment method, e.g., `15,000 VND` minimum for MoMo); maximum is up to 8 digits (`99,999,999` VND) for general non-card methods and up to 12 digits (`999,999,999,999` VND) for card payments depending on card network ([Supported Currencies](https://docs.stripe.com/currencies), accessed 2026-11-23; [MoMo Payments](https://docs.stripe.com/payments/momo), accessed 2026-11-23).

### 4. Status model and late success after expiry

- **PaymentIntent `status` (`7` values)**:
  - Non-terminal: `requires_payment_method`, `requires_confirmation`, `requires_action`, `processing`, `requires_capture` (when `capture_method: manual`).
  - Terminal: `succeeded`, `canceled` ([The PaymentIntent Object](https://docs.stripe.com/api/payment_intents/object), accessed 2026-11-23; [Payment Intents Lifecycle](https://docs.stripe.com/payments/paymentintents/lifecycle), accessed 2026-11-23).
  - **Backward transitions on failure**: When a confirmation/payment attempt fails, Stripe emits `payment_intent.payment_failed`, records `last_payment_error`, and returns `PaymentIntent.status` **back to `requires_payment_method`** so the same `pi_...` can be retried (unless canceled, or auto-canceled after hitting the confirmation limit) ([Verifying Payment Status](https://docs.stripe.com/payments/payment-intents/verifying-status), accessed 2026-11-23; [Confirm a PaymentIntent](https://docs.stripe.com/api/payment_intents/confirm), accessed 2026-11-23).
  - **Two-step capture**: With `capture_method: manual`, authorized funds land in `requires_capture`; partial capture transitions to `succeeded` and releases the remainder (unless `final_capture=false` multicapture is used), while uncaptured holds auto-cancel to `canceled` after ~7 days ([Place a Hold](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method), accessed 2026-11-23; [Multicapture](https://docs.stripe.com/payments/multicapture), accessed 2026-11-23).
- **CheckoutSession `status` + `payment_status`**: `status` is `open`, `complete`, or `expired`, while `payment_status` is `unpaid`, `paid`, or `no_payment_required`. A `complete` session with a delayed payment method still has `payment_status: unpaid` until `checkout.session.async_payment_succeeded` ([The Checkout Session Object](https://docs.stripe.com/api/checkout/sessions/object), accessed 2026-11-23; [Konbini Payments](https://docs.stripe.com/payments/konbini/accept-a-payment), accessed 2026-11-23).
- **Late success after expiry**: **Confirmed possible**. For **Konbini**, Stripe explicitly documents that a customer who generated a payment slip before `expires_at` can still pay at the cash register *after* `expires_at` and succeed (Stripe delays `payment_intent.payment_failed` with a buffer) ([Konbini Payments Direct API](https://docs.stripe.com/payments/konbini/accept-a-payment?payment-ui=direct-api), accessed 2026-11-23). For **Multibanco**, Stripe holds the `PaymentIntent` in `processing` for a 4-day post-expiry buffer; funds arriving after that buffer trigger an automatic refund ([Multibanco Payments](https://docs.stripe.com/payments/multibanco/accept-a-payment), accessed 2026-11-23).

### 5. Final result delivery, authoritativeness, signature scheme, and retry

- **Authoritative channel**: Server-to-server **Webhooks** (`POST` JSON; TLS 1.2/1.3 required in live mode) or authoritative server API retrieval. Stripe explicitly warns not to fulfill orders from client redirects (`return_url` / `success_url`) or client SDK promises because customers may close the browser before fulfillment runs ([Verifying Payment Status](https://docs.stripe.com/payments/payment-intents/verifying-status), accessed 2026-11-23).
- **Signature scheme**: `Stripe-Signature` header (`t=<unix_sec>,v1=<hmac_sha256_hex>,...`, plus optional unsigned `v0`/`secret`/`destination`/`payload` metadata that must be ignored). Verified via constant-time check of `HMAC-SHA256(whsec, "${t}.${rawBody}")` over the **unmodified raw HTTP body** with a timestamp tolerance (default 5 minutes in Stripe SDKs) ([Stripe Webhooks](https://docs.stripe.com/webhooks), accessed 2026-11-23).
- **Retry & ordering**: Any non-`2xx` status (including `3xx` redirects), timeout, or TLS failure triggers retries: **up to 3 days with exponential backoff in live mode** (`3` retries over a few hours in sandbox), regenerating `t` and `v1` on each attempt. Stripe explicitly states **event ordering is not guaranteed** and supports both snapshot (`data.object`) and thin event payloads ([Stripe Webhooks](https://docs.stripe.com/webhooks), accessed 2026-11-23).

### 6. Expiry or timeout of an unpaid attempt

- **PaymentIntents API**: **No automatic expiration**—a `PaymentIntent` stays open indefinitely until `POST /v1/payment_intents/:id/cancel` (except payment-method voucher deadlines like Konbini/Boleto/Multibanco, excessive failed confirmations, or 7-day uncaptured holds in `requires_capture`) ([Compare Checkout Sessions and Payment Intents](https://docs.stripe.com/payments/checkout-sessions-and-payment-intents-comparison), accessed 2026-11-23; [Cancel a PaymentIntent](https://docs.stripe.com/api/payment_intents/cancel), accessed 2026-11-23).
- **Checkout Sessions API**: Expires at `expires_at` (**30 minutes to 24 hours**, default **24 hours**), emitting `checkout.session.expired`, and can be expired early via `POST /v1/checkout/sessions/:id/expire` ([Create a Checkout Session](https://docs.stripe.com/api/checkout/sessions/create), accessed 2026-11-23; [Expire a Checkout Session](https://docs.stripe.com/api/checkout/sessions/expire), accessed 2026-11-23). Note: You cannot directly cancel a Checkout Session's underlying `PaymentIntent` unless its status is `requires_capture`; you must expire the Checkout Session instead ([Cancel a PaymentIntent](https://docs.stripe.com/api/payment_intents/cancel), accessed 2026-11-23).

### 7. Refund API

- `POST /v1/refunds` targeting `payment_intent` (or `charge`) ([Create a Refund](https://docs.stripe.com/api/refunds/create), accessed 2026-11-23).
- **Partial & multiple refunds**: Fully supported—multiple partial refunds can be issued against one `PaymentIntent` / `Charge` up to the original captured amount ([Create a Refund](https://docs.stripe.com/api/refunds/create), accessed 2026-11-23; [Refund and Cancel Payments](https://docs.stripe.com/refunds), accessed 2026-11-23). Refunds issued shortly after capture may execute as a card **reversal** (`destination_details.card.type = 'reversal'`) ([Refund and Cancel Payments](https://docs.stripe.com/refunds), accessed 2026-11-23).
- **Asynchronous completion**: `Refund.status` has 5 states: `pending`, `requires_action` (customer must submit bank details via Stripe email for non-refundable methods like Konbini/PromptPay), `succeeded`, `failed`, and `canceled`. Refunds pending due to `insufficient_funds` remain `pending` up to 45 days before failing; bank-rejected refunds can transition to `failed` up to 30 days later ([The Refund Object](https://docs.stripe.com/api/refunds/object), accessed 2026-11-23; [Refund and Cancel Payments](https://docs.stripe.com/refunds), accessed 2026-11-23). Emits `refund.created`, `refund.updated`, `refund.failed`, and `charge.refunded` webhooks ([Refund and Cancel Payments](https://docs.stripe.com/refunds), accessed 2026-11-23).
- **Idempotency key support**: First-class `Idempotency-Key` HTTP header (up to 255 chars, UUID v4 recommended) on all API v1 `POST` calls, including `/v1/refunds` and `/v1/payment_intents`. API v1 caches the first executed status code and body (even `500`s, returning `Idempotent-Replayed: true`) for at least **24 hours**; parameter mismatches or concurrent in-flight requests return `409 Conflict` without caching ([Idempotent Requests](https://docs.stripe.com/api/idempotent_requests), accessed 2026-11-23; [Advanced Error Handling](https://docs.stripe.com/error-low-level), accessed 2026-11-23). The official `stripe-node` SDK automatically attaches a `stripe-node-retry-<uuid>` `Idempotency-Key` on `POST` requests and defaults `maxNetworkRetries` to `2` via `PlatformFunctions.getDefaultMaxNetworkRetries()` ([`stripe-node` `RequestSender.ts`](https://raw.githubusercontent.com/stripe/stripe-node/master/src/RequestSender.ts), accessed 2026-11-23; [`stripe-node` `stripe.core.ts`](https://raw.githubusercontent.com/stripe/stripe-node/master/src/stripe.core.ts), accessed 2026-11-23; [`stripe-node` `PlatformFunctions.ts`](https://raw.githubusercontent.com/stripe/stripe-node/master/src/platform/PlatformFunctions.ts), accessed 2026-11-23).

### 8. Duplicate callback or webhook behaviour

- Stripe explicitly warns that webhook endpoints can receive the **same `Event` (`evt_...`) multiple times**, AND that Stripe can occasionally generate **two distinct `Event` objects** for the same state change—meaning integrations must deduplicate both by `event.id` and by `(data.object.id, event.type)` ([Stripe Webhooks](https://docs.stripe.com/webhooks), accessed 2026-11-23).
- Events are **not guaranteed to arrive in order**, and `created` has 1-second granularity so timestamps cannot be used for ordering or deduplication ([Stripe Webhooks](https://docs.stripe.com/webhooks), accessed 2026-11-23).

## Contract implications

### Domain model (`amount` / `currency` / references) — Ticket 03

- **Store integer minor units in Core, convert per gateway in adapters**: Store `Payment.amount` in canonical currency minor units (for VND, integer dong—e.g., `100000` for 100,000 VND, matching ISO 4217 zero-decimal, ZaloPay, and Stripe). **Do not** store VNPay's `×100` scaled value in the domain model; let the VNPay plugin multiply/divide by `100` at the port boundary (and validate VNPay's `>= 5,000 VND` / Stripe settlement minimums).
- **Separate merchant attempt ID from provider reference**: `PaymentTransaction` must own a globally unique `attemptId` (used as VNPay's `vnp_TxnRef` and ZaloPay's `yymmdd_<id>` `app_trans_id`, avoiding their daily-uniqueness and retry-collision traps), plus a **nullable** `providerRef` (`VARCHAR(255)`, case-sensitive) because VNPay (`vnp_TransactionNo`) and ZaloPay (`zp_trans_id`) do not supply a provider transaction ID at initiation time.
- **Add an opaque `providerMetadata` / extension bag on `PaymentTransaction` and `Refund`**: Required to carry gateway-specific fields needed for later calls without polluting Core—e.g., VNPay's `vnp_CreateDate` (`vnp_TransactionDate` for `querydr`/`refund`), ZaloPay's `zp_trans_id` vs `app_trans_id`, and Stripe's `latest_charge` / `payment_intent` vs `checkout.session` IDs.
- **Refund data hook constraints**: A `Refund` attaches to a succeeded **`PaymentTransaction`** (not merely `Payment`), must track requested vs cumulative refunded amount (`1 PaymentTransaction : N Refunds`), and needs its own `refundAttemptId` (for VNPay `vnp_RequestId`, ZaloPay `m_refund_id`, Stripe `Idempotency-Key`) plus nullable `providerRefundId` and asynchronous `RefundStatus` (`PENDING` / `SUCCEEDED` / `FAILED`).

### State machine (`statuses` and races) — Ticket 04

- **Keep `PaymentTransaction` single-use and forward-only, absorbing Stripe's retry loop inside the adapter/transaction**: Because VNPay and ZaloPay create one-shot attempts while Stripe `PaymentIntent` transitions backward to `requires_payment_method` on decline, Core should map each checkout confirmation attempt cleanly and **cancel/expire superseded `PaymentIntent`s or `CheckoutSession`s** when creating a new `PaymentTransaction` (e.g., switching from Stripe to VNPay).
- **Support `PENDING` / `PROCESSING`, `SUSPECT_HOLD` (or manual-review/uncaptured), `EXPIRED`, `FAILED`, `SUCCEEDED`, and `CANCELED`**: VNPay `vnp_ResponseCode=07` (debited under fraud suspicion), `vnp_TransactionStatus=04` (bank-debited reversal), and Stripe `requires_capture` prove success/failure is not binary; Core needs either an explicit non-terminal/hold state or a reconciliation-flagged outcome so debited funds are never silently treated as unpaid.
- **Explicitly resolve return-vs-webhook and late-success-after-expiry races**:
  - Browser return URLs **must never** transition `PaymentTransaction` to `SUCCEEDED`; they may only trigger an optimistic UI wait or enqueue an authoritative status query (`querydr` / `/v2/query` / Stripe `retrieve`).
  - Core **must enforce an explicit expiry/timeout transition** (`EXPIRED`) driven by an internal scheduler/job (because ZaloPay emits no failure/expiry callback and Stripe `PaymentIntent` never expires automatically).
  - If an authoritative webhook/IPN reports `SUCCEEDED` **after** a `PaymentTransaction` transitioned to `EXPIRED`: Core must **not** silently drop it! Either transition `Payment` to `SUCCEEDED` if no competing `PaymentTransaction` has succeeded (late capture wins before another attempt succeeds), or mark the late attempt as **`LATE_SUCCESS_CONFLICT` / duplicate-paid requiring automatic or manual refund** if another `PaymentTransaction` already settled the `Payment`.
- **Reconciliation polling is mandatory, not optional**: Because ZaloPay sends callbacks only on success and VNPay/ZaloPay refunds emit no webhooks, the state machine must tolerate transitions driven by scheduled active status queries (`query` / `querydr` / `query_refund`) in addition to webhooks.

### `PaymentGateway` port (operations and fields) — Ticket 05

- **Initiation return shape must be a discriminated union (`NextAction`)**: `initiatePayment()` cannot return just a `redirectUrl`. Define a union covering: `REDIRECT` (VNPay `vpcpay.html`, Stripe Checkout `url`, Stripe `redirect_to_url`, ZaloPay `order_url`), `QR_CODE` (ZaloPay `qr_code` VietQR string, Stripe `next_action.*_display_qr_code`), `CLIENT_SDK` (Stripe `client_secret`, ZaloPay `zp_trans_token`), and `VOUCHER` (Stripe Konbini/Boleto), with an optional `expiresAt` and `providerRef` (nullable!).
- **Required port operations**:
  - `initiateTransaction(input)` -> `{ providerRef?: string, nextAction, rawMetadata }`
  - `queryTransaction(ref)` -> normalized status + `providerRef` + `amount` + `paidAt` + `rawCode` (essential for ZaloPay polling, VNPay return verification, and Stripe reconciliation)
  - `cancelOrExpireAttempt(ref)` -> best-effort cancellation (supported via ZaloPay `/v2/cancel`, Stripe `payment_intents/:id/cancel` or `checkout/sessions/:id/expire`; no-op / unsupported capability flag for VNPay)
  - `verifyAndParseWebhook(rawRequest)` -> **must accept unmodified raw body bytes + headers + query params** (Stripe signs raw HTTP JSON body via `Stripe-Signature`; ZaloPay POSTs JSON with `key2` HMAC over `req.body.data`; VNPay uses `GET` query params with `HMAC-SHA512` `vnp_SecureHash`) and return `{ providerEventId?, attemptId, providerRef?, normalizedStatus, ackPayload }` (so VNPay can reply `RspCode: "00"/"02"`, ZaloPay `return_code: 1/2`, and Stripe HTTP `200`).
  - `createRefund(input)` and `queryRefund(ref)` -> refund initiation returning `{ providerRefundId?, status: PENDING | SUCCEEDED | FAILED }`, plus mandatory `queryRefund` because VNPay (`05`/`06`) and ZaloPay (`return_code=3`) complete asynchronously without webhooks.
- **Provider capability & idempotency metadata**: Expose gateway capability flags (e.g., `supportsCancel`, `supportsPartialRefund`, `supportsMultiplePartialRefunds`, `supportsRefundWebhook`) and pass Core's deterministic `idempotencyKey` (`attemptId` / `refundAttemptId`) into every write call so Stripe uses `Idempotency-Key`, VNPay maps it to `vnp_TxnRef`/`vnp_RequestId`, and ZaloPay formats `yymmdd_...` `app_trans_id`/`m_refund_id`.
