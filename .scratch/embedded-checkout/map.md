# Map: Embedded Checkout with Pricing Plans and Webhooks

## Destination

An Organization sells Pricing Plans from any web page by pasting a snippet from the Console. The snippet loads one shared PayBridge script that shows a Pricing Table. When a Customer picks a Pricing Plan, they pay in a checkout window served by PayBridge, using any PaymentGateway the Organization has enabled. The browser starts Payments with a public Publishable Key, and the Amount always comes from the Pricing Plan on the server. The Organization learns the outcome of every Payment, from the checkout or its own API, through signed Webhooks delivered to its Webhook Endpoints.

- **State today**:
  - Core writes Payment Events to `core_outbox_events` with five types: `PaymentCreated`, `PaymentSucceeded`, `PaymentCancelled`, `PaymentExpired`, `PaymentRequiresReview`. The outbox relay adds them to the `core-outbox` BullMQ queue, but **nothing consumes that queue**. There is no failed or refund Payment Event.
  - Payments are created only through the payments API with an API Key. The caller supplies the Upstream Reference. Payment Expiry is 30 minutes to 24 hours, with a default of 30 minutes.
  - Identity owns API Keys and resolves callers to a `Principal` (Organization and optional User). Payment Core exposes a public port. Lint rules forbid importing a module's internals.
  - The Console is behind sign-in and a BFF (ADR 0004). There is no public web app for Customers.

## Decisions so far

Settled by grilling on 2026-11-26:

- **Webhooks are required.** Anything the browser reports can be forged, so the Organization learns that a Payment succeeded from a signed Webhook, or by reading the Payment with its API Key as a fallback. Browser callbacks are for display only.
- **One-time payments only.** A Pricing Plan is paid once. Subscriptions are planned for later and are a separate effort.
- **The browser starts Payments with a Publishable Key** (ADR 0009). The key is public, works only for the Organization's Pricing Plans, needs a list of allowed websites, is rate-limited per key and per IP, and an Organization can hold several for rotation. The Amount is never taken from the browser.
- **A Pricing Plan is a template.** A Payment copies the Amount (and the Pricing Plan's name) when it is created and keeps a reference to the Pricing Plan. Editing or archiving the Pricing Plan never touches existing Payments. A Pricing Plan with Payments is archived, never deleted.
- **Gateways.** The checkout shows the PaymentGateways the Organization has enabled, optionally limited per Pricing Plan. It handles every NextAction kind itself: redirect, QR, and client SDK (Stripe.js).
- **One shared, versioned SDK** hosted by PayBridge. The Console generates only a snippet (`data-key`, `data-table`, ...), not a file per Pricing Plan. Pricing data loads at runtime, so Console changes show immediately.
- **Payment UI runs in a PayBridge-hosted iframe/modal.** The host page draws only the price cards. `frame-ancestors` restricts which sites may frame it.
- **Knowing who bought: both.** The snippet may pass a Customer Reference (the Organization's user id), and/or the checkout may ask for an email. Either travels on the Payment and its Webhooks. A forged reference only means someone paid for someone else.
- **Upstream Reference** for checkout Payments is generated by PayBridge.
- **Double clicks and reopening** continue the same open Payment in the same browser session for the same Pricing Plan and Customer Reference, until its Payment Expiry.
- **Return after a redirect** lands on a PayBridge page that shows the result, then forwards to the success or cancel URL from the Pricing Plan or the snippet, or else back to the host page.
- **Webhooks cover every Payment**, not only checkout ones.
- **Webhook delivery:**
  - an Organization can have several Webhook Endpoints, each with its own signing secret and chosen event kinds;
  - deliveries are signed with HMAC;
  - delivery is at least once, with no ordering guarantee, and receivers drop duplicates by event id;
  - failed deliveries are retried with exponential backoff for about three days, then marked failed;
  - the Console shows delivery history and allows a manual resend.
- **When the checkout cannot sell** (archived Pricing Plan, suspended Organization, no gateway enabled, website not allowed, revoked key): the button shows "Payment is not available right now" with no reason. The developer reason goes only to the browser console. Payments already under way finish normally.
- **Permissions**:
  - only the Organization Admin manages Pricing Plans, Pricing Tables, Publishable Keys and Webhook Endpoints;
  - Operators can view Pricing Plans and Webhook deliveries and resend a delivery, but cannot change anything else;
  - Super Admins can do everything, labelled as the platform.
- **No Customer emails.** PayBridge sends no receipts. That is the Organization's job after the Webhook.
- **Refunds** use the existing Refund flow. Nothing is checkout-specific.
- **Browser callbacks** (`onSuccess`, `onCancel`, `onError`) are optional, for pages that update without a redirect. `success-url` covers the common case.
- **Pricing Tables**:
  - a snippet shows a Pricing Table of one to three Pricing Plans;
  - the Pricing Table is stored in the Console with an order and an optional recommended Pricing Plan, so it can be changed without re-pasting;
  - a single-plan snippet is a one-column Pricing Table.
- **Content edits.** A Pricing Plan's name, description and features can change any time and show immediately. Webhooks carry the Pricing Plan id and its name at purchase.
- **Feature lines** are plain text, each marked included (✓) or not included (✗). No HTML.
- **Look**: main colour, light or dark, language (vi/en), button text. No custom CSS.
- **Customer Reference** is set once per snippet and applies to whichever Pricing Plan is picked.
- **Payment Expiry** of checkout Payments comes from the Pricing Plan, with a default and editable within the existing range.
- **A Pricing Plan can sit in several Pricing Tables.** Archiving it shows that column as unavailable in all of them. The Console warns first.
- **A Pricing Table can be deleted**, because it holds no money. Pages that embed it show "unavailable".

Settled while writing the spec (2026-11-26):

- **Three test seams.** API over HTTP, real-HTTP Webhook delivery to a local receiver started in the test, and Playwright for the SDK, checkout and new Console pages.
- **The SDK and checkout page live in a new public app (`apps/checkout`)**, separate from the Console, because the Console sits behind sign-in and the BFF.
- **Webhook event kinds are today's five Payment Event types plus `webhook.test`.** In grilling, `payment.failed` and `refund.succeeded` were mentioned as examples. They wait until Core emits such Payment Events.
- **Outbound Webhooks are protected against SSRF in production.** Confirmed by the user. Each delivery:
  - resolves DNS and refuses private, loopback and link-local addresses (including cloud metadata);
  - connects to the checked IP;
  - follows no redirects;
  - uses HTTPS only.

  Localhost is allowed in development and tests. If an Organization ever needs an internal receiver, a Super Admin exception can be added.

- **Module placement** (an architecture choice made while writing the spec, not put to the user): Pricing Plans and Pricing Tables in a new checkout module; Publishable Keys in identity next to API Keys; Webhook Endpoints and deliveries in a new webhooks module that consumes the `core-outbox` queue. Each new module has its own table prefix.

Confirmed by the user after the spec was written (2026-11-26):

- A Pricing Plan with no Payments can be deleted outright, and an archived one can be restored.
- Webhook Endpoint secrets can be rolled with an overlap window, during which both secrets sign deliveries. A test event can be sent to an endpoint.

## Follow-ups (out of scope)

- Subscriptions and recurring billing.
- Pricing Tables with more than three Pricing Plans, monthly/yearly toggles, trials, coupons, taxes, quantities.
- Custom CSS or HTML in Pricing Tables.
- Currencies other than VND.
- Receipts or any email to Customers.
- `payment.failed` and `refund.*` Webhook kinds, which need new Payment Events in Core.
- Ordered or exactly-once Webhooks.
- A hosted payment link with no host page.
- Pricing Table analytics.
